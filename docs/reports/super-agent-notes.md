# Super-agent 材料笔记（复盘用）

三份材料说的不是一回事，引用前先分清：文章写的是**已经跑起来的原型**；theory 文档写的是**目标形态**，原型里没有；spike 是我们自己的对照实验。`diagram-architecture.png` 画的是 theory 的目标形态（契约树、视图编译器、产物 DAG），不是文章的架构。下文用「文章 §x」指 `Super-agent 设计探索：迈向更自主的 Agent 系统`（B 站 opus，2026-10-31），「theory §x」指 `multi-agent-arch-spike/docs/多agent组合的统一理论.md`，「PROJECT §x」指 spike 的 `PROJECT.md`。

## 1. 分层：两层，没有中间层

| 层 | 是谁 | 职责 | 明确不做 |
| --- | --- | --- | --- |
| Router | 常驻的单个 LLM Session | 承接所有人类交互、准入、归属、交付、全局记忆 | 不执行具体任务，不深入单任务内部拆解，"甚至可以不配备 Bash 工具"（文章 §2.1） |
| Worker | 上下文隔离的执行 Session | 专注单一任务，挂完整执行工具 | 不直接与人类交互，推理与工具调用不外泄到信道（文章 §2.2） |

- 只有两层，没有经理/监督者层。Router 层"内部不必局限于单个 Session"，Worker 内部可以再开 Subagent、甚至本身就是一个 Agent Team，对 Router 透明（文章 §2.2），这是自相似，不是第三层。
- 它和 Agent Team 的分界线：Team Lead 要拆子步骤、高频协调、背很重的推理负载；Router 只管任务之间。文章给了一个判定句：如果约束一个 Team 的主会话不亲自执行、只对外交互并分派，那它"也可以视为这种双层架构"（§2.1）。
- 层间边界压缩成一句原文，"Router 不管技术细节，Worker 不管权限边界"（架构图底注，与文章 §2.1 一致）。
- 产物流转：事件 → Fast/Slow 两级过滤 → 未订阅事件进 Router → Router 建 Worker 并建立 Thread 订阅 → 同 Thread 后续事件程序直通 Worker → Worker 向 Router 汇报结论 → Router 统一对外回复、更新全局记忆（§2.2、§3.2）。Worker 越界可取消订阅或交回 Router 重派（§3.2）。
- 原型里没有产物 DAG，产物主要靠 Thread 与 PR 关联；DAG 是 theory 的目标形态（theory §1.3）。

## 2. 靠什么保证质量

- **事件质量靠两级过滤**：程序层做 Fast Path（来源、群组、白名单等确定性条件），模型只处理候选事件做 Slow Path（文章 §3.1）。动机是"高噪音、低触发率"，每条都过模型成本不可承受。
- **不用共享状态造一致性，用订阅造一致性**：同层 Worker 不点对点通信，多对多订阅同一 Thread，各自收到同一事件后自行发现冲突；跨任务协调由 Router 中转（§2.2、§3.2）。没有"黑板"这个概念，等价物是 Thread + 事件流。
- **上下文控制在预算内**：Inline（近期会用到就内联）/ Spill（超预算或低频只留引用），再叠加链式召回（对象给唯一 ID，注入时内联下一跳 ID，可沿引用图逐跳展开）（§3.3）。
- **Watchdog 是主系统之外的独立控制回路**：一个独立 Session，定时消息驱动；不仅看进程存活和接口报错，还由模型判断"Worker 是否有实质进展、方向是否偏离"，异常时介入修复，偶发故障持续复查（§6）。维护者能用自然语言问它原因，也能让它在线改提示词和触发规则。
- **验收在文章里是人**：人的角色上移到决策与验收（§1、§9）。独立验收者、产物图、验收者不得是被验收者子节点这些规则，是 theory 补的目标形态（theory §4.2），原型没有。
- **重试与评审回路：三份材料都没有**。文章只有 Watchdog 的"持续复查直至恢复"，没有任务级重试策略、没有评审 agent。
- **成本控制是显式的取舍**：用更多 token 换更短更稳的完成时间（§7.1）；投机执行故意消耗后台算力，结果没价值就丢弃（§3.4）；IM 信道硬性"单次回复不超过 100 词"（§4.2）。

## 3. 明确反对什么、踩过什么坑

反对（都是原文的判断句）：

1. 让用户管理 Session。"Session 应当是系统的实现细节，而不应是用户的认知负担"，手动管 Session 是"从底层 LLM API 延续下来的设计惯性"（§2、§8.2）。
2. Router 深入单任务细节（§2.1）。
3. Worker 直接对人说话，多个 Session 各自回复造成交互混乱（§2.2）。
4. Worker 之间直接通信（§2.2、§3.2）。
5. 过早水平切分 Router，"牺牲全局上下文的连续性"（§2.1、§7.2）。
6. 把执行环境同步上云再重建：本地有未提交修改、私有凭据、内网依赖，"成本很高，还容易出现信息遗漏"（§5.2）。
7. 靠提示词保证分工（§7.1 的消融实验直接打掉了这条路）。

坑：

- **单 Session + Subagent 的委派不可靠**：中性提示下 5 次运行一次都没调用 Subagent，所有工作挤在主 Session 被新消息打断，p95 到 29.5 分钟。改成"优先委派"后 4/5 委派，仍有 1 次判断工作"很小"自己干，形成长尾（§7.1）。结论：分工要由系统结构保证，不能由模型临场判断。
- **没有直通，代价是纯开销**：完成时间基本不变，但 Router 决定数 +30%、读缓存 token 2323 万 → 3177 万（+37%）（§7.1）。
- **长程记忆是主要瓶颈**：链式召回只解决近期任务与会话历史，跨月尺度上"长程记忆成为制约可扩展性的主要瓶颈"（§8.1）。
- **安全**：云端 Agent Loop 一旦被入侵或提示词注入攻破，连接的全部端侧设备都可能被控制；凭据只要进过上下文就有泄露风险（§8.4）。
- **实验自身的局限**（作者自陈，§7）：合成负载、编码工作用"只消耗时间的工具"代替、消息间隔与工作时长按 1/4 缩放。测的是调度与协作，不是执行能力；每种方案只跑 5 次。
- 还没解决的：Router 何时该分片、脱离 Session 后产品形态怎么定、跨实例 A2A、安全隐私（§8 全节）。

## 5. 与我们的做法对应 / 不对应

对应的（可以直接引用文章支撑我们的规则）：

- L1 管理层 ↔ Router：拆解、派单、验收、汇报、维护状态，不做实现（`AGENTS.md` §0、§1）。
- L2 一职能一 agent、互不通信、冲突由 L1 重派 ↔ Worker 隔离加订阅直通（`AGENTS.md` §1.1、§1.2）。
- 只认落盘产物 ↔ 产物验收（`AGENTS.md` §1.3；文章 §9 的人只做验收）。
- `docs/STATE.md` 唯一事实来源 ↔ Router 的全局记忆加世界存储。
- 关键节点由不参与实现的独立 agent 复核 ↔ theory §4.2 的独立验收者（这条文章里没有，是 theory 的）。

不对应的三处，复盘时优先看：

1. **我们的 L2 是一次性的，文章 Worker 是持久加订阅的**。因此在拓扑上我们等于文章 §7.1 的"去掉直通"对照组：所有续派事件都要 L1 重新理解、重新写 prompt。文章给的价码是决定数 +30%、token +37%、质量不变。我们目前没有 token 记账，只能先承认付了这笔钱，无法量化。
2. **我们没有 Router 之外的独立回路**。Watchdog 盯的是"这个 Worker 有没有实质进展"，我们的等价物只有 L1 自己发现或用户发现。`AGENTS.md` §8.3 承认同一上下文自审不算验收，但没规定无进展时谁介入、多久介入。
3. **我们没有 ID 与引用图，派单 prompt 就是全部上下文**。文章 §3.3 说注入过少会逼模型反复调工具读（"浪费上下文窗口，就是浪费模型的智能"），theory §9 把这个叫上下文饥饿。若复盘显示 L2 反复读同一批文件或反问已知信息，就是我们按"一次性全给"写的 prompt 不够自足，而不是子 agent 能力问题。

可以拿来检验我们这套的四条（都有判据，不只是观点）：

- **A. 直通假设**：统计同一任务续派时 L1 的 token 与决策数，对比"全量重写 prompt"与"只增量"两种派法。先在 `STATE.md` 里补一行 token 记账，否则这条永远证伪不了。
- **B. 分工靠结构不靠提示**：文章 0/5 的委派失败率可以直接套。翻历史派单，凡 prompt 里写"必须委托给子 agent"的场次，看 L1 是否仍自己动手。
- **C. 无进展检测延迟**：用任务派发时间与重派时间差算子 agent 静默失败的发现延迟。这条不需要新实验，历史时间戳够用。
- **D. 组合是最后手段的证据**：`PROJECT.md` 的六条公理第 4 条与 needle 实验结果一致，可 grep 定位的活不值得多开一层递归。这条支持我们默认不轻易派生 L3。
