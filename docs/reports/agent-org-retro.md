# 分层 agent 协作复盘（2026-11-07）

对象：从 0 到开源发布，L0（人）— L1（管理层会话）— L2（一次性子 agent）这套做法的实际效果。
对照材料：`docs/reports/super-agent-notes.md`（super agent 原型 + 理论文档 + 我们自己的 spike）。

先说清：我们不是 super agent，是**只用子 agent 搭起来的原始近似**。没有 Router 常驻会话、没有事件订阅、没有 Watchdog、没有产物 DAG。下文对照只用于校准。

## 一、实际形态与规模

| 维度 | 做法 |
| --- | --- |
| 层数 | 两层：L1 接人拆单验收；L2 执行，彼此不通信 |
| L2 生命周期 | 一次性为主；少数线程用续派（产品规格、真机脚本、Android UI、链接分享） |
| 并发 | 2–4 路，试探式加档 |
| 文件域隔离 | git worktree（`scripts/wt.sh`） |
| 记忆 | `docs/STATE.md` 手写 + 27 份文档 + 13 份报告 |
| 验收 | 每条任务自带可重跑脚本，只认落盘证据 |

规模：45+ 次派单、56 个提交（4 次来自 worktree 合并）、283 个受版本控制的文件、25,534 行 Kotlin、15 条脚本。

## 二、对的六件事（有实证）

1. **上下文隔离换来真并行。** 4 路同时跑过：内核、Windows、Android、验证各占一个文件域，靠 worktree 隔离。
2. **只认落盘产物。** 每个 agent 必须给命令 + 路径 + 输出，「我做完了」不算数。
3. **派单模板把边界写死。** 40+ 次派单里越界只有一次，且那次是发现边界外的缺陷后按规矩上报。
4. **一次性 agent 是文档的冷启动测试。** 撞出两处真问题：`addPublicMagnet` 的判重语义（任务书写错、按代码纠正）、系统分享的透明 Activity 在真机上不会被创建（照文档写会静默丢数据）。
5. **反向变异成为习惯。** 至少五次「把实现改错、看断言是否变红」：私有标记、去重策略、窗口撤销、分享者预算、AlertType 补表。另有两条恒真断言被这样揪出。
6. **A/B 对照把猜测变成数字。** Doze 后退后台 2 分钟：无前台服务断链 23 次、重连 20 次、恢复 20 秒；加了前台服务后全部为 0。同一把尺子量前后。

## 三、不对的六件事（也都有实证）

1. **没有直通，代价落在 L1 的笔上。** 每条续派都要重写背景（内核现状、目录边界、验收命令）。文章给的对照组数字是决定数 +30%、token +37%，我们的形态正落在那一组。
2. **没有 Watchdog。** Windows tracker 首轮 429 直接消失；内核崩溃那条线程跑一小时没落一个文件，靠我主动去问才发现。平均发现延迟 30–60 分钟。
3. **全局记忆靠手写，必然过期。** 里程碑表停在 M1 阶段，直到 L0 问「为什么 M2/M3 没做」才发现——实际那两阶段大部分已完成。
4. **提交纪律没有落到执行层。** 出现四次 `git add -A` 把别人在写的改动卷进提交：`.probe/`（class 文件）、`.wrangler/` 与 `node_modules/.mf/`、Android 的保活改动被写进「WebView spike」的提交。
5. **设备不是资源锁。** 两次同一台手机被两个 agent 同时驱动：一次造成「SAF 选不到文件」的假失败（独占后 6/6 成功），一次直接打断验收。
6. **验收脚本自身也会撒谎。** 恒真断言（grep 永远匹配不到）、状态依赖导致的假失败（tracker 验收单独跑 phase b 得 21/2，完整跑 47/0）、以及测试工具自身限制被测对象能力（mock 的 10 秒读超时让「分享者活不过十几秒」这个缺陷隐藏了很久）。

## 四、管理层自己犯的错（这部分最该留档）

1. **照搬估算不核对。** 说 WebRTC 占 24 MB、APK 会从 51 MB 降到 27 MB；实测是 12.5 MB 的差（那个 12.3 MB 的 dex 是 Compose 不是 WebRTC）。数字错了两处：把 spike 的估算当结论、把安装占用当安装包体积。
2. **把别人的操作算成系统的。** `wrangler login` 的日志出现 Successfully logged in，我理解成自动完成；实际是 L0 在浏览器里点的。
3. **用自己的口径覆盖证据。** 一度要求「分享者预算改 TTL」作为兜底，而根因是 core 把访客预算与分享者等待预算混成一个值——正确的修法在 core，不在宿主。
4. **STATE 过期。** 唯一事实来源没有随阶段推进更新，导致 L0 对进度产生错误印象。

## 五、与 super agent 的对照

| 它的做法 | 我们的做法 | 差别后果 |
| --- | --- | --- |
| Router 常驻、有全局记忆 | L1 常驻，记忆是手写 STATE | 可丢、可过期 |
| Worker 订阅 Thread、事件直通 | 无直通，每次重写 prompt | 重复叙述、token 浪费 |
| Watchdog 独立判断有无进展 | 无，靠巡视或用户发现 | 静默失败 30–60 分钟才发现 |
| 两层、无中间层 | 同 | 一致 |
| Worker 不直接对人说话 | 同 | 一致 |
| 同层不点对点通信 | 同 | 一致 |
| 产物 DAG / 契约树 | 只有文件路径约定 | 缺少产物血缘 |
| token 记账 | 无 | 无法判断性价比 |

结构上最像；机制上差最远的是**直通**与**Watchdog**——都不是算力问题，是信息通路问题。

## 六、可执行的改进（按性价比）

1. **提交按路径，不按全集。** 子 agent 禁止 `git add -A`；L1 提交时用显式 pathspec。
2. **设备锁文件。** 派单写明「本任务独占 <序列号> N 分钟」，用 `artifacts/.device-lock-<serial>` 互斥。
3. **给 L1 加常驻卡片。** 每模块 5 行现状（接口、已知坑、验收命令），续派时引用而非重写。
4. **轻量 Watchdog。** 程序判据即可：20 分钟内工作区无写入就触发状态查询。
5. **STATE 半自动生成。** 从 `git log` + 报告标题生成初稿，人只改判断。
6. **断言自带反向期望。** 每条断言声明它在什么输入下必须红，或脚本内置 `--mutant`。

## 七、适用边界

- 适合：任务可拆、验收可脚本化、产物落在文件系统里的工程工作。
- 不适合：需要长程记忆与反复打磨同一套品味的工作，一次性 agent 会不断重新推导同样结论。
- 上限：**L1 的带宽就是并发上限。** 我能同时跟住约 4 条活跃线程，超过就开始记不清谁在改哪个文件——与文章里「人只能跟 3–5 个活跃 Session」是同一个约束，只是换成了 agent 自己。
