# 分层 agent 协作复盘（2026-11-07）

对象：本项目从 0 到交付的整个过程中，L0（人）— L1（管理层会话）—L2（一次性子 agent）这套做法的实际效果。
对照材料：`docs/reports/super-agent-notes.md`（super agent 原型 + 理论文档 + 我们自己的 spike）。

先说清一件事：我们做的不是 super agent，是一个**只用子 agent 搭起来的原始近似**。它没有 Router 常驻会话、没有事件订阅、没有 Watchdog、没有产物 DAG。因此下文对照只用于**校准**，不用于宣称"我们实现了它"。

## 一、实际的运行形态

| 维度 | 我们怎么做的 |
| --- | --- |
| 层数 | 两层：L1 接人、拆单、验收；L2 执行，彼此不通信 |
| L2 生命周期 | 一次性。少数例外：三条线程用 `send_message` 续派（产品规格、真机脚本、Android UI） |
| 并发 | 2–4 路，按 AGENTS §10 试探式加档 |
| 文件域隔离 | 冲突时开 git worktree（`scripts/wt.sh`），完成合并 |
| 记忆 | `docs/STATE.md` 手写 + 34 份文档 + 12 份报告 |
| 验收 | 每条任务自带可重跑脚本，只认落盘证据 |

规模：40+ 次派单，35+ 提交（4 次来自 worktree 合并），69,901 行 Kotlin，15 条脚本。

## 二、对的六件事（都有实证）

1. **上下文隔离换来真并行。** 4 路并行跑过：内核、Windows、Android、验证各占一个文件域，靠 worktree 隔离，没有互相踩。同期单线程不可能做到。
2. **只认落盘产物，验收骗不了人。** 每个 agent 都被要求给"命令 + 路径 + 输出"，而不是"我做完了"。这条挡掉了旧项目那种"文档说 X、实际没做"。
3. **派单模板强制把边界写死。** "只改 core/、不改 app/"这类约束在 40 次派单里被遵守，例外只有一次（一个 agent 顺手发现了边界外的崩溃，按规矩上报而不是自己改）。
4. **一次性 agent 是文档的冷启动测试。** 它只拿到 prompt，做不成就是文档有洞。此次撞出两处：`addPublicMagnet` 对已有条目返回 duplicate（任务书写错，按代码纠正）、系统分享的透明 Activity 在真机上根本不会被创建（照文档写会静默丢数据）。
5. **反向变异成为习惯。** 至少三次主动"把实现改错、看断言是否变红"：私有种子标记、去重策略、窗口撤销。另有两条恒真断言被这样揪出来（`team.no_teammate_events` 的 grep 永远匹配不到）。
6. **跨模块的坏消息能被带上来。** 例：Android 端发现公开会话崩溃 → 报 L1 → 由内核线程定位到 AlertType 映射表缺项。层级没有把坏消息吃掉。

## 三、不对的六件事（也都有实证）

1. **没有直通，代价落在 L1 的笔上。** 文章给的对照是：Worker 不能直接接收同 Thread 事件时，决定数 +30%、token +37%。我们的形态正落在这一组——每条续派都要我重写背景（内核现状、目录边界、验收命令）。省下的只有上下文，花掉的是重复叙述。
2. **没有 Watchdog，静默失败靠人发现。** 实例：Windows tracker 首轮 429 直接消失，无任何痕迹；内核崩溃那条线程跑了一小时没落一个文件，是我主动去问才知道它卡在哪。文章里这活是主系统之外的独立会话干的。
3. **全局记忆靠手写，必然过期。** `STATE.md` 的里程碑表停在 M1 阶段，直到 L0 问"为什么 M2/M3 没做"才被发现——实际 M2/M3 大部分已完成。信息没丢，是汇总那一份没维护。
4. **提交纪律没有落到执行层。** 出现过三次 `git add -A` 把别人在写的改动卷进提交：`.probe/`（class 文件）、`.wrangler/` 与 `node_modules/.mf/`（临时产物）、app 的 5 个文件被写进"core: 跨网分享窗口"。内容后来都对，但历史不可读。
5. **设备不是资源锁。** 两次同一台手机被两个 agent 同时驱动：一次造成"SAF 选不到文件"的假失败（独占后 6/6 成功），一次直接打断验收。
6. **验收脚本自身也是代码，也会撒谎。** 除了恒真断言，还有两例"看起来失败其实是脚本状态依赖"：tracker 验收单独跑 phase b 得到 21/2，完整跑则 47/0。判断"是不是产品缺陷"这件事，本身要花管理成本。

## 四、和 super agent 的对照

| 它的做法 | 我们的做法 | 差别后果 |
| --- | --- | --- |
| Router 常驻、有全局记忆 | L1 会话常驻，记忆是手写 STATE | 记忆可丢、可过期 |
| Worker 订阅 Thread、事件直通 | 无直通，每次重写 prompt | 重复叙述、token 浪费 |
| Watchdog 独立判断"有无进展" | 无，靠 L1 巡视或用户发现 | 静默失败平均发现延迟 30–60 min |
| 两层、无中间层 | 同 | 一致；这条我们做对了 |
| Worker 不直接对人说话 | 同 | 一致 |
| 同层不点对点通信 | 同 | 一致；也避免了协同式开发的混乱 |
| 产物 DAG / 契约树 | 只有文件路径约定 | 缺少"这份产物由谁产生、被谁消费"的图 |
| 成本按 token 记账 | 没有记账 | 无法做"值不值"的定量判断 |

结论：**结构上最像、机制上差最远的两处是"直通"与"Watchdog"**。这两样都不是算力问题，是信息通路问题。

## 五、可执行的改进（按性价比排序）

1. **提交按路径，不按全集。** 子 agent 禁止 `git add -A`；L1 提交时用显式 pathspec。可立刻执行，零成本。
2. **设备锁。** 派单时写死"本任务独占 <序列号> N 分钟"，用 `artifacts/.device-lock-<serial>` 文件互斥。已实际踩过两次。
3. **给 L1 加"常驻卡片"。** 把每个模块的现状压缩成 5 行（当前接口、已知坑、验收命令），续派时直接引用而不是重写。等价于给 Router 加一块小记忆。
4. **轻量 Watchdog。** 不引入模型，只用程序判据：每个在跑 agent 若 20 分钟内没有新的工作区写入（`git status` 与 `artifacts/` mtime 都不变），就触发一次状态查询。能覆盖本次的两次静默失败。
5. **STATE 半自动生成。** 里程碑与"已完成"从 `git log` + 报告标题生成初稿，人只改判断。能避免这次的过期。
6. **验收脚本加自检。** 每条断言附一个"反向期望"（在什么输入下它必须红），或在脚本里内置 `--mutant` 开关。本次三次手工变异证明有效，值得制度化。

## 六、这套形态适合什么

- 适合：任务可拆、验收可脚本化、产物落在文件系统里的工程工作。这正是本项目的样子。
- 不适合：需要长程记忆与跨任务推理的工作（例如反复迭代同一个设计品味），一次性 agent 会不断重新推导同样的结论。
- 边界：L1 的带宽就是并发上限。我能同时跟住的活跃线程大约是 4 条；超过之后，我开始忘记谁在改哪个文件——这一点和文章里"人只能跟 3–5 个活跃 Session"是同一个约束，只是换成了 agent 自己。
