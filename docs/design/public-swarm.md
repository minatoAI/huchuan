# 公开种子社区设计（M3）

- 版本 pub2 · 2026-11-06 · 执行层设计 agent（只读）· 唯一产物：本文件；pub1 的六条待拍板已由 L1 裁决，见 §10
- 范围：M3「公开种子社区」；私有模式、跨网穿透、链接分享不在本文。输入：`product-spec.md`（P2/P3/P4）、`protocol.md`、`nat-traversal.md`、`tech-options.md` §6.4、`core/m1/` 现状
- 证据口径：本仓代码与实测 > libtorrent4j 2.1.0-39 制品（javap 实取）> BEP/官方文档 > 推演（标「推」）
- 前提（AGENTS §9，本文不改）：私有与公开两套 SessionManager；PEX 无会话级开关，只能 per-torrent 0x380000；私有侧固定关 DHT/LSD

## 0. 七问七答

1. **数据模型**：同一个 `GroupFile` 加 `scope` 一个判别字段，公开条目多一个 `magnet`、元数据可空。不建新表、不建新页（§1）。
2. **开关**：DHT 开、PEX 开、公共 tracker 只认种子自带的、LSD 关。开的是「IP + 公开 infohash」，关掉的是「磁力无源」的可达性（§2）。
3. **磁力**：磁力必存、种子到手再存；元数据只从 swarm 的 ut_metadata 拿，不接索引站；失败一律一句话、不弹窗（§3.1）。
4. **群内加速**：不是新机制，是「把成员端点注入公开 swarm」；价值是补源与局域网提速，不做 0x53 分片（§4）。
5. **合规**：不做索引、不做搜索、不做举报（没有接收方）；MVP 只做「本地移除 + 屏蔽该 infohash」（§5）。
6. **UI**：页面级新增 **0**，行内/弹层新增 **4 处**；P2 不加聚合行（已裁决，product-spec M3 行已同步，§6.3）。
7. **隔离**：独立端口段、独立目录、独立状态、按需启停；限速只能「每会话各自封顶」，跨会话共享令牌桶在 libtorrent 里不存在（§7）。

## 1. 数据模型：一条实体，一个判别字段

产品要的是「同一个群的同一种文件列表」：P3 一屏里私有文件与公开种子并列，点进去都是 P4。两套表 = 两套列表 = 两套状态机，必然漂移。群内同步链路（file.add 签名广播 → file.list 全量 → 256 条上限，protocol §7）公开条目直接复用，**零新消息类型**（protocol §9 已定「M3 私有层零变更」）。

### 1.1 字段增量（`Protocol.FileEntry`）

| 字段 | 私有 | 公开 | 说明 |
|---|---|---|---|
| `scope` | private | public | 判别字段，缺省 private；旧 state.json 读回来零迁移 |
| `magnet` | 可空 | 必填 | 规范化：`xt=urn:btih:<40 hex>`，保留 `tr` |
| `size` / `pieceSize` | 建种时已知 | 未知填 0 | 元数据到手后本地回填，不改签名、不回广播 |

- 签名域不动：`huchuan/file1/v1` 已覆盖 fileId（= infohash）+ name + size + pieceSize + addedBy + addedAt（protocol §1.2），「谁把它加进群」有据可查；`magnet` 本来就不在签名域内（Protocol.kt:174-179），公开条目额外要求 `xt == fileId`，接收方本地校验即可。
- **一个文件私有发一次、公开发一次 = 两行两个 infohash**。private=1 写在 info 字典里（BEP 27），改它必然改 infohash，这是 BEP 层面的必然；UI 用 chip 区分（§6）。size=0 不是缺陷：真实尺寸由 info 字典自身保证，谁都能解析自查，不需要信任发布者。
- **同群内按 fileId 去重**：同一 infohash 以两种 scope 出现时只留 private 一条（L1 裁决）；入表前先查 scope，后到的那条丢弃并记日志。
- `seeders` 语义随 scope 变：私有 = 本群做种者；公开 = 公开会话 `numSeeds()`（群外也算）。同一字段同一文案「做种 n」。

### 1.2 判别归判别，安全归安全

加种前一律用 `TorrentInfo.priv()` 决定进哪个会话，**不信 `scope` 字段**：

- 传输中的 `scope` 可被转发方篡改（不在签名域内），但它最多影响 UI 与列表归属；若公开会话收到 private=1 的元数据，libtorrent 按 BEP 27 自动禁掉该 torrent 的 DHT/PEX，效果等同「只在群内传」，不需要我们额外处理。
- 反向（私有会话收到 private=0）不可能发生：私有侧只接受本群 `file.add` 的 fileId，且会话 ip_filter 只放行私网。

### 1.3 存哪

| 东西 | 位置 | 理由 |
|---|---|---|
| 条目、评论、签名 | 群 `state.json`（现状） | 同一实体同一库；公开不等于脱离群 |
| 公开会话的 torrent / resume / 元数据 | `<data>/public/`（新增） | 会话级隔离，见 §7 |
| 公开下载落盘 | `<data>/public/data/` | tech-options §6.4「独立下载目录」的最小实现 |

## 2. 公开会话的四个开关

### 2.1 泄露什么、关掉损失什么

| 开关 | 打开后谁知道 | 关掉损失 | 默认 |
|---|---|---|---|
| DHT | 相连的 DHT 节点知道「这个 IP 在下载 infohash X」；任何人可查该 infohash 拿到本机公网 IP | 只有磁力、没有 tracker 的种子找不到任何 peer，功能直接失效 | **开** |
| 公共 tracker | tracker 运营方拿到 IP + infohash + 进度 | 少一条 peer 来源；swarm 稀疏时更慢 | **只认种子自带的 tr** |
| PEX | 同一 swarm 的 peer 互相知道 | 少一条来源；DHT 已覆盖 | **开** |
| LSD | 同网段任意 BT 客户端知道本机在下载 infohash X | 同网段发现；但群成员走消息层（§4），不需要 | **关** |

- LSD 关的理由不是「怕被发现」，而是它把公开 infohash 广播给本网段所有装了 BT 的人，而局域网发现我们已有自己的通道：收益为零，暴露面净增。
- **PEX 没有会话级开关**（AGENTS §9）。公开条目必须显式**不设** 0x380000；实现上不复用 `BtSession`——它加种时无条件 `PRIVATE_FLAGS.or_(extraFlags)`（BtSession.kt:555），加参数等于把「忘了传」变成隐私事故。另起 `PublicBtSession`，flags 从一个「显式清零」的常量出发。

### 2.2 我们发布种子时带不带 tracker

- **不带**：发布只建 magnet（xt/dn/xl），靠 DHT 找 peer。第三方 tracker 会拿到用户 IP + infohash，换来的只是「DHT 被拦时还能连」这条边际收益，M3 不值。
- 导入的磁力**原样保留**它自带的 `tr`——那是发布者的选择，不是我们的。
- **我方 tracker 不承载公开种子**：自带 tracker 的 info_hash 槽位是 `groupHash20`、passkey 由 kGrp 派生（protocol §3.2），语义是「群成员登记消息端口」。公开种子只在 DHT 上 announce ——服务端不持有任何公开 infohash，合规面与计费面都不扩大（§5）。

### 2.3 会话参数（`PublicBtSession`）

| 项 | 值 | 依据 |
|---|---|---|
| `enable_dht` | true，bootstrap 用库默认 | 关了就找不到 peer |
| `enable_lsd` | false | §2.1 |
| `enable_upnp` / `enable_natpmp` | 有非休眠公开条目时 true、结束撤销，否则 false（已裁决） | nat-traversal §7：不做映射 = 本机在公网永不可入站；与私有侧跨网窗口同一套策略 |
| `enable_*_utp` | 显式 true | 公网 peer 里 uTP 占比高；私有侧至今没写死（nat-traversal §13-5），公开侧写死并注明理由 |
| `listen_interfaces` / ip_filter | `0.0.0.0:6881` 起顺延；**不设 ip_filter** | 设了就永远连不到公网 peer |
| per-torrent flags | DISABLE_DHT / PEX / LSD 全部不设 | §2.1 |

- 可选（不进 M3）：P7 一个开关「公开种子只在本群传输」= 公开条目也套 0x380000、不 announce 任何 tracker。实现成本极低（复用同一常量），但要新增 UI 元素，排 M3.1。

## 3. 磁力导入

- **磁力必存**（`magnet` 字段）；**种子到手后再存**：发布路径本来就有 .torrent，导入路径先只有磁力，`MetadataReceivedAlert` 到手后把 `handle.torrentFile()` 写 `<data>/public/meta/<infohash>.torrent`，重启不再重拉。
- **群内只传磁力，不传 .torrent**：帧上限 65533 B、内联 .torrent 47 KiB（protocol §5），大种子必然超；公开条目不缺元数据来源（swarm 自己就有），这条老问题（STATE.md 已知风险）在公开侧直接消失。
- 元数据只有一条来路：**从 swarm 取**（BEP 9 ut_metadata，libtorrent 内置）。不接索引站、不做元数据缓存服务、不内置热门种子库——那等于我们成了索引（§5.1）。
- 现成 API（javap 实取）：`SessionManager.download(String magnetUri, File saveDir, torrent_flags_t flags)`、`MetadataReceivedAlert` / `MetadataFailedAlert`、`TorrentHandle.torrentFile()`。

### 3.1 失败怎么表现

| 失败 | 时机 | 表现 | 落点 |
|---|---|---|---|
| 磁力语法/格式错 | 提交时 | 输入框下一行「链接无法识别」，不建条目 | P3 弹层 |
| 拿不到元数据 | 条目已建、无 peer | 条目正常存在（名字取 `dn`，缺省「未命名种子」），状态「等待来源」；周期重试，不弹窗 | P3 行 / P4 |
| 点了激活仍无 peer | 60 s 内 numPeers=0（阈值可调） | 复用现成文案「连不上做种者，重试」 | P4 |
| 元数据解析失败/超限 | 收到即判 | 「文件信息无效」，条目保留、开关禁用 | P4 |
| 磁盘不足 | 开始落盘 | 「空间不足」，条目回休眠 | P4 |

核心取舍：**无元数据不报错**。BT 拉元数据本来就是分钟级，报错等于逼用户反复点重试；只有用户主动要它下载（激活）之后才给「连不上」。尺寸未知时 P3 行不显示大小，P4 显示「等待来源」而不是 0 B。

## 4. 「群内互相加速」在公开种子上是什么

公开条目 = 普通 BT 种子，同一 infohash 天然同一个 swarm。群成员的价值只有两条，都不引入新机制：

1. **注入已确认可达的端点**：`peer.announce` 已广播 dev→(host, btPort)，`connectPeer` 走 swig（BtSession.kt:261-269）。缺的只是「公开会话端口」这一个字段。
2. **补 availability**：新发布的种子在公网往往只有发布者一个源；群成员是第二、第三个源，把「能不能下完」从概率问题变成确定性问题。

### 4.1 唯一需要的协议增量

- `peer.announce` 加可选字段 `pubBtPort`（u16；0/缺省 = 本机无公开会话）。现有 `btPort` 是私有会话端口（protocol §10、mDNS TXT `bt`），公开会话是另一个端口（§7.1），混用会把成员拨到错误的会话上。
- 旧实现按「未知字段忽略」照收（protocol §5），不需要版本升级。不加 `pubBtHost`：M3 先服务「同局域网 / 同一 NAT 后 / 一方有公网 IP」三种组合，跨网打洞留给 nat-traversal 的穿透档。
- 拨号沿用 nat-traversal §10（可达性决定方向）；公开条目要**对每个成员各拨一次**，不能被「已有 1 条 peer」吃掉（team-acceleration §1.3 的短路口径）。

### 4.2 价值多大（不吹）

| 场景 | 群成员这条边值多少 |
|---|---|
| 同局域网 | 实测 25.4 MB/s 量级（nat-traversal §9 引 docs/66）；公网做种者受上行 2.5–12 MB/s 限制 → 快 2–10× |
| 公网 swarm 已有多个源 | 接近 0：libtorrent 按速率选源，只多一条候选 |
| 新发布、公网 0 源 | 决定性：没有群成员就没有第二个源 |
| 双方都在 NAT 后、公网 peer 都连不上 | 决定性：群成员端点是消息层已经握手确认过的 |

准确说法是**补源 + 局域网提速**，不是「人多就快」，与 team-acceleration §1.2 一致：不动 picker 就不承诺吞吐。不做 0x53 分片（E0 实测 D=1.1394 < 1.25 判定线，STATE.md 已完成项）、不做群内专属 swarm、不做任何中继。

## 5. 安全与合规

### 5.1 责任边界（先写死再谈功能）

- **不做索引**：没有公开种子目录、没有搜索、没有热门榜、不抓公共索引站。公开种子的可见范围 = 它被发进的那个群。
- **不托管内容**：没有我们的存储、没有我们的中转；自带 tracker 不承载公开 infohash（§2.2）。
- 责任落点：发布者对自己发布的内容负责；群是邀请制，进群即已建立信任边界；应用只提供 BT 能力与群内广播。
- 唯一要写进 UI 的一句（是「会怎样」，不是法务文本）：发布时在 P4 显示一次「公开后任何 BT 客户端都能下载」。只出现一次，不弹二次确认框（AGENTS §4.3）。

### 5.2 举报：不做；MVP 只做本地移除 + 屏蔽

举报要有接收方。我们没有账号体系、没有审核团队；没人处理的按钮比没有更糟——用户会以为处理了。可用的对策是把控制权放回本地：

| 动作 | 位置 | 语义 | 成本 |
|---|---|---|---|
| 移除 | P4「…」菜单 | 只从本机列表消失；不广播 file.del（M2 才有，protocol §9）；不删磁盘文件 | 1 个菜单项 + 本地标记 |
| 屏蔽 infohash | 同一次操作顺带写本地黑名单 | 之后任何来源（群广播、磁力导入）再出现同一 infohash 都不入库 | 1 张表（≤256 条 LRU） |

- 屏蔽不广播：一个人的黑名单不该变成群的审查，也避免被用来打人。不做：举报、举报记录、封禁名单同步、内容评级、年龄门。
- 其他已知面：成员滥发沿用每群 256 条上限（protocol §7），兜底就是移除 + 屏蔽；下载来的文件可能带恶意内容，P4 来源行显示发布者而不是「未知」，不做扫描——没有可靠判据，做了等于假装安全。

## 6. UI 增量

### 6.1 上限：页面级 0，行内/弹层 4

| 位置 | 增量 | 计入元素 | 文案 |
|---|---|---|---|
| P3 行 | 一枚 `公开` chip（在状态 chip 左侧） | 行内，计 0（product-spec 计数口径：列表项内部操作不计） | `公开` |
| P3「添加文件」 | 变成弹层：选择文件 / 导入磁力 | 弹层，非页面元素 | `选择文件` `导入磁力` |
| P3 弹层内 | 磁力输入框 + 导入 | 同上 | `粘贴磁力链接` `导入` |
| P4「…」菜单 | 私有条目「公开到群外」／公开条目「移除」 | 菜单项，计 0 | `公开到群外` `移除` |

- 页面元素数不变：P3 仍 3 个（文件列表 / 添加文件 / 成员），P4 仍 5 个（信息 / 进度 / 开关 / 菜单 / 评论）。发布提示写在 P4 页内（来源行旁一行），不弹窗；「公开到群外」只在文件处于「做种中」时出现（机器能判的事不让用户点，AGENTS §4.7）。
- 发布用 `SEED_MODE` 加种，免二次全量哈希（10 GB 重扫一遍盘是几十秒的假死）；前提是私有侧刚校验完，数据已知完好。
- Windows：壳仍负责「选择文件」（原生 `IFileOpenDialog`，见 daemon-api §3.3）；「导入磁力」是纯前端文本输入，壳与 daemon 都不用改。

### 6.2 两类条目靠三样区分

1. `公开` chip 只在公开条目出现，位置固定；私有条目没有任何 chip 补位（不出现「私有」字样）。
2. 状态 chip 语义不变（做种中 / 下载中 / 休眠）；公开条目多出的唯一状态是「等待来源」。
3. 入口不同：私有条目只能由「选择文件」产生；公开条目只能由「导入磁力」或 P4「公开到群外」产生。

不在一页里加「私有/公开」分段：那是第二套列表，违反一页一功能；同一个文件两行时，用户要的是「一眼看出差在哪」，不是切换视图。

### 6.3 P2 不动（已裁决，product-spec M3 行已同步）

product-spec §7 M3 行原写「P2 列表增加『公开种子』一行」，**已改为**「公开条目在各群 P3 列表内，行内加『公开』chip」（本次落稿）。理由：① 一页一功能——P2 的唯一功能是「进入某个群组」，公开种子行是第二个功能（浏览）；② 合规——跨群汇总公开条目 = 我们做了索引，与 §5.1 直接矛盾。将来若要跨群视图，最小形态只能是「我所在各群的公开条目」过滤视图（复用 P3 组件 + `scope=public`），不能扩成全站目录。

## 7. 双会话隔离

### 7.1 端口与资源

| 维度 | 私有 | 公开 |
|---|---|---|
| 消息层 TLS | 47100–47199（PeerServer.kt:11） | 不开 |
| BT 监听 / DHT | 51413 起顺延 100（BtSession.kt:87）／DHT 关 | **6881 起顺延**／DHT 与 BT 同端口（libtorrent 在 listen 端口收 UDP） |
| 生命周期 | 常驻（M1 现状） | **按需**：有非休眠公开条目才 start；全部休眠/移除即 stop（顺带撤端口映射） |
| 连接上限 | 不设（群 ≤32 人） | `connectionsLimit=200`、`activeDownloads=3`、`activeSeeds=20`（javap 实取） |
| 存储 / 日志 | `<data>/bt`／`sess=priv` | `<data>/public/{meta,data}`／`sess=pub` |
| 关闭顺序 | 后 | 先（先撤映射，再停会话） |

- 两段端口不重叠；一个会话绑定失败时不得落到对方段。6881 是 BT 客户端的惯例端口，公开会话本来就承认自己是 BT 客户端，用它不额外泄露；私有会话继续避开它。
- 按需启停的代价：DHT 冷启动 + bootstrap 要几秒到几十秒，第一次激活会慢一拍，可接受——比让每个用户后台常驻 DHT 好。线程/内存是否随 stop 完全释放**待测**，记为 M3 验收项。
- 硬约束：权限状态不对时**不得先起公开会话**（AGENTS §9 的既有教训同样适用；公开侧虽不依赖 mDNS，但监听 + 映射全开，状态错位更难排查）。

### 7.2 限速：只能各管各的

事实：`upload_rate_limit` / `download_rate_limit` 是 **session 级**（BtSession.kt:308-336），`setUploadLimit` 是 torrent 级（BtSession.kt:299-304），libtorrent 没有跨会话共享令牌桶。两个会话 = 两个独立预算，「P7 全局限速」只有三种可能语义：

1. 每会话各自封顶（总峰值最多 2×）——**M3 取这一条**；
2. 只压私有会话（公开不限）——公开下载跑满，用户会以为是 bug；
3. 给公开会话单开一行——多一个设置项，但语义诚实。

裁决（§10-3）：M3 取 1，P7 该项说明位写「两种下载各自不超过此值」；2× 上限 M3 接受，M3.1 再评估第 3 种。单文件限速（P4）是 torrent 级，对公开条目照旧生效，无需改。
